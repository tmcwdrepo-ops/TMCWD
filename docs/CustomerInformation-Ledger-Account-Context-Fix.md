# Customer Information Ledger account context

Verified 2026-10-12 (Asia/Manila), source and synthetic testing only.

Root cause: the search-result click assigned `item.accountNumber` to `txtSearch` but called `loadCustomer(item.customerId)` without the selected account ID. `GetCustomerInformationData` returns the customer's current-address account, or first account, as `selectedAccount`. `populatePage` then assigned that default account to `_currentAccountNumber` while leaving the searched number visible. Thus selecting 01-010010 could display 01-010010 while Ledger requested 01-010003. This was not a stale closure: Ledger reads the mutable state at click time. `switchToAccount` existed but had no callers in this view; there are no rendered account-row selection handlers or separate hidden Ledger account inputs.

Search now retains `item.accountId` and finds that exact account in the returned customer accounts before populating the page. An absent match fails visibly without substituting the default account. The existing `setActiveAccountNumber` updates both `_currentAccountNumber` and the displayed search value on initial load, AJAX population and direct account switching; null selection clears both. Ledger, Bills and adjustment-history actions continue reading that same state. A pending or failed selection retains the previously applied account, and an older load response cannot overwrite a newer selection. Previous/Next remain full-page customer navigation; their links are now initialized on initial load as well as AJAX population.
