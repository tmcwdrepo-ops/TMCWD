# Account Ledger HTTP 500 and duplicate placeholder fix — October 8, 2026

The authenticated Data API now returns **HTTP 200** for development account `01-010020`, another account with bills, and an account with no financial transactions. The local `debit_credit_memos` table remains absent. No schema or application financial data was changed.

1. **Why DCM was queried.** The initial canonical history aggregator included `DebitCreditMemos` because its entity, DbSet and CRUD service existed. That assumed code presence meant deployed persistence. The regression harness also created a temporary DCM table, masking the deployment gap. Previous startup/authentication checks did not exercise an authenticated account ledger read. Those completion checks were insufficient to establish runtime success.

2. **Repository and deployment audit.** The existing pieces are `TMCWD.Data/Entities/DebitCreditMemo.cs`, `UserDbContext.DebitCreditMemos`, `DebitCreditMemoService`, its interface, `DebitCreditMemoController`, and standalone schema script `TMCWD/database/debit_credit_memos.sql`. The script defines a table consistent with the entity. No DCM script was found under the current `TMCWD/TMCWD.Data/Database` migration directory. Read-only inspection of the configured local development database confirmed the deployed table count is zero. DCM therefore has model/CRUD/schema code but undeployed persistence in this installation. The existing standalone DDL was not applied: DCM is outside Phase 6G and its deployment is not required to load the ledger.

3. **History source removed.** Removed the DCM query and event aggregation from `AccountLedgerService.Get`. A `ponytail:` comment records the undeployed limitation and the Phase 6K integration point. There is no exception-driven missing-table catch, per-request schema probe, invented schema, migration or fabricated memo event. Bills, contracts, children, payments, cancellation records, penalties and existing supported billing adjustments retain their authoritative sources. Installment/payment calculations are unchanged.

4. **Exact source/document files changed in this fix.** Earlier dirty work was preserved.

    - `TMCWD/TMCWD.Data/Services/AccountLedgerService.cs` — remove undeployed DCM source
    - `TMCWD/TMCWD.Application/wwwroot/js/collections.js` — exclude Ledger from generic Coming Soon registration
    - `TMCWD/TMCWD.Application/wwwroot/js/account-ledger.js` — prevent a queued close event from aborting a newly reopened dialog
    - `TMCWD/TMCWD.Application/Views/Collections/Collections.cshtml` — content-based versioning for the corrected Collections script
    - `TMCWD/TMCWD.Application/Views/Billing/Collections.cshtml` — same script versioning
    - `tests/BillingRegression/AccountLedgerRegression.cs` — replace DCM memo expectations with empty/populated deployed-schema checks and a SQL guard
    - `tests/BillingRegression/Program.cs` — stop creating a temporary DCM table
    - `tests/BillingRegression/collections-browser-regression.cjs` — single opening, no Coming Soon, empty states, genuine HTTP failure and rapid close/reopen coverage
    - `docs/Phase6G-Canonical-Account-Ledger.md` — superseding runtime-fix report reference
    - `docs/Phase6G-Account-Ledger-HTTP500-Fix.md` — this report

    `.tmp/ledger-fix-verification` contains a read-only local verification helper; build output and diagnostic logs are also isolated under `.tmp`. No DCM entity/DbSet/CRUD implementation or SQL script was changed.

6. **Empty ledger behavior.** An account with no transactions still returns the authoritative header, zero TotalBalance/CollectibleOtherCharges and empty Bills, OtherCharges and History arrays. The browser retains all three tabs and displays their empty states. Regression readers reject any SQL containing `debit_credit_memos`, and the harness no longer provisions that table. Empty and populated ledger tests verify supported data without depending on optional persistence. Existing repeated-read checks continue to verify no mutation of financial state.

7. **Obsolete Ledger Coming Soon behavior.** Collections attached a generic click listener to every `.link-chip`; Ledger fell through to `showComingSoonModal`. Its existing delegated canonical handler also ran, producing two UIs. The generic registration now excludes `[data-modal="ledger"]`. The canonical handler remains the sole owner of Ledger clicks. Other placeholder actions retain their existing behavior; no CSS hiding workaround was used. Actual browser tests verify one canonical dialog, one ledger request, and no visible Coming Soon overlay. Both Collections views now use `asp-append-version="true"` so updated script content receives a fresh cache key. A final browser rerun exposed a queued native-dialog close event aborting the next opening; the shared close handler now ignores that old event when the dialog has already reopened, with a deterministic rapid-reopen regression.
